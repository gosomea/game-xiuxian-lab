# game-template 0.3 → 0.4 手工迁移指南

0.4.0 是破坏性模板升级：单层 `src/game/<feature>/` 改为
`src/game/<domain>/<package>/`，capability catalog 从 schema v1 改为 v2。
模板不会自动同步或改写派生项目；每个项目按自身 `TEMPLATE_VERSION` 选择性迁移。

## 迁移前

1. 提交或备份当前工作树，记录派生项目使用的模板版本。
2. 运行现有版本的 `python3 tools/verify/run_all.py --with-tests`，先确认基线是绿的。
3. 列出 `src/game/` 下所有单层目录。不要把目录名直接当成新 package；先逐项判断玩家可感知行为、状态生命周期和删除单元。

## 1. 设计两级映射

第一层 domain 只导航，推荐 `actors/`、`abilities/`、`systems/`、`shared/`，也可使用项目需要的其他 `snake_case` 名称。第二层 package 是可独立删除的叶子包。

```text
# 错误：combat 是宽泛领域，运行时文件直接堆在领域根
src/game/combat/damage.gd
src/game/combat/targeting.gd

# 正确：每个叶子包有明确行为、生命周期和删除边界
src/game/abilities/spirit_quake/
src/game/systems/targeting/
```

不要把 M1/M2/M3、prototype、phase_2 等开发阶段名保留为长期运行时包或类型边界。

## 2. 确认数据与场景所有权

- 有自然领域所有者的 Component 留在所有者包，即使其他包会读取它。
- 只有没有自然所有者的跨包数据契约进入 `src/game/shared/<contract>/`；先写 owning note。
- `src/levels/` 只留完整关卡和关卡专属编排。
- 可复用场景、功能专属 UI、材质、贴图与音效移到所属叶子包附近。
- Capability 与 `test_<basename>.gd` 必须在叶子包根；资源可以继续使用包内子目录。

## 3. 用 Godot 编辑器移动

优先在 Godot FileSystem 面板中逐包移动或重命名，让编辑器同步 `.uid` 与场景 `ext_resource`。移动后检查：

- `.tscn` / `.tres` / GDScript 中的 `res://game/...` 引用；
- `src/tests/test_runner.gd` 的测试路径；
- `src/data/vocabulary/` 中指向 Component 脚本的元数据；
- `load()` / `preload()` / SheetLoader 的字符串路径；
- 项目设置、Autoload 和导出配置中的资源路径。

如果不得不在编辑器外移动，保留原 `.uid` 文件，关闭 Godot 后移除可再生的 `src/.godot/` 缓存，再执行下一节的 import。不要删除源资源来“解决”悬空引用。

## 4. 整理关卡根脚本

`src/levels/<name>.tscn` 的根节点若挂脚本，脚本 basename 必须为 `<name>.gd`。例如把 `arena.tscn` 根挂的 `m3_flow.gd` 改为 `arena.gd`。功能子场景和子节点脚本不受这条同名规则限制。

模板 sandbox 的 0.4 形态是根节点直接挂 `src/levels/sandbox.gd`，不再保留只为承载报告脚本而存在的 `Report` 子节点。

## 5. 引入 policy 与 catalog v2

复制 0.4 的 `design/package_policy.json` 和 `tools/verify/verify_packages.py`，并把门禁接入本项目的 `run_all.py`、lefthook 与 CI。

默认阈值是超过 4 个 Capability 或 12 个非测试 GDScript。超限时优先拆包；确属同一删除单元才登记豁免：

```json
{
  "package": "systems/example",
  "note": "notes/implemented/tech/YYYY-MM-DD-example.md",
  "reason": "为什么这些文件仍属于同一个状态生命周期和删除单元"
}
```

note 必须真实存在于 `notes/implemented/`、第三行是 `Status: implemented`，reason 不得为空。

运行 `python3 tools/gen/gen_capability_catalog.py` 生成 schema v2。下游脚本若读取 v1 的 `feature` / `features`，需改读 capability 的 `domain` / `package` 与顶层 `domains` / `packages`；0.4 不提供兼容层。

## 6. 重新导入并验证

```bash
godot --headless --path src --import
python3 tools/gen/gen_vocabulary_index.py
python3 tools/gen/gen_capability_catalog.py
python3 tools/verify/verify_packages.py
python3 tools/verify/verify_scenes.py
python3 tools/verify/run_all.py
python3 tools/verify/run_all.py --with-tests
```

最后把派生项目的 `TEMPLATE_VERSION` 更新为 `0.4.0`，并记录本项目选择保留、修改或跳过了哪些模板变化。

## 7. 人工孤儿审查

0.4 不加入启发式孤儿脚本硬门禁，因为 Godot `class_name`、动态 `load()` 与运行时实例化会制造大量误报。迁移完成后人工执行：

1. 在编辑器对准备删除或遗留的场景/资源使用 **View Owners**。
2. 全仓搜索旧 `res://game/<old-package>/` 与旧类名。
3. 检查 `class_name` 动态实例化、字符串 `load()`、Autoload、signal 连接和资源导出字段。
4. 打开并运行受影响的完整关卡，不只运行单元测试场景。
