# Note: 角色移动子实验套件

Status: implemented

## 问题

角色移动原先由 `movement_garden.tscn` 与 `mountain_realm.tscn` 同时承担能力验证、镜头、动作表现、地形接触、御剑高低差和综合美术展示。群山宗门已经形成满意的综合场景，继续直接在其中调试镜头或动作，会让局部实验受复杂地形与美术干扰，也增加场景编排和角色能力之间的耦合。顶层实验目录原先每个模块只有一个入口，无法如实表达一个移动大项下的多个子实验及其状态。

## 决策

使用者确认本方案并授权实现；本记录先于实现落盘，七个叶子场景先后落地后，于集成阶段迁移 implemented。角色移动保留为一个顶层模块，顶层入口为移动子实验目录；各子实验围绕一个可回答的问题独立运行。旧庭院与群山资产和场景全部保留，未覆盖、未删除。

子实验地图（七项全部落地，均可从子实验目录进入）：

| 子实验 | 核心问题 | 定位 | 场景 |
|---|---|---|---|
| 镜头实验室 | 跟随、缓动、死区、前视、缩放、旋转与遮挡怎样配合移动？ | 灰盒对比场 | `camera_lab.tscn` |
| 人物动作工作台 | 待机、起步、跑动、转身、跳跃、御剑、降落及其过渡是否清楚？ | 空白动作棚 | `motion_stage.tscn` |
| 地形接触训练场 | 斜坡、台阶、墙角、窄路和边缘上的移动与碰撞是否稳定？ | 物理训练场 | `ground_contact_course.tscn` |
| 御剑飞行训练场 | 起飞、升降、悬停、穿越、转向和落点选择是否可控？ | 立体路线场 | `sword_flight_course.tscn` |
| 状态切换压力场 | 能力切换、失焦、重置、碰撞和边缘时机是否正确清账？ | 可视化压力场 | `state_transition_lab.tscn` |
| 移动庭院 | 小范围地面移动和旧资产回归 | 已有基线 | `movement_garden.tscn` |
| 群山宗门 | 三项移动能力在完整空间与美术中的组合体验 | 已有综合场景 | `mountain_realm.tscn` |

顶层 `character_movement` 条目只指向移动子实验目录（`movement_lab_hub.tscn`）。子实验清单由 `src/data/content/character_movement_subexperiments.json` 维护 `id / title / stage / question / status / scene`；hub 只读取与校验该文件，不硬编码入口，未落地的条目不得伪造路径或标为就绪。未把子实验塞成新的顶层玩法模块，也未为嵌套目录改造通用 `core/`。

### 架构边界（实现后仍然成立）

- `SwordsmanMovement`、`Jump`、`SwordFlight` 仍是仅有的三项移动 Capability；各能力只经 `SwordsmanMotionComponent` 意图字段与 TagRegistry 协作，禁止相互直接引用。七个场景均未新增第四项能力。
- 角色根仍是唯一 `move_and_slide()` 提交点。子实验不直接写角色 `velocity`、移动意图或 Capability 内部状态，只调用角色公开输入 API。
- 动作表现属于 `game/actors/swordsman/`，只读取 `actual_velocity / on_floor / flight_active / aim_direction` 等公共运动数据，不把动画帧、动作播放完毕或场景节点作为物理规则。
- 镜头比较、障碍布局、调试 HUD 和实验控制属于对应 `levels/experiments/character_movement/` 子场景。实验结论稳定并出现第二个真实消费者后才抽取共享节点：`movement_lab_input.gd`（镜头实验室与人物动作工作台两个消费者）即按此约定产生。其余片段未提前抽入 `core/`。
- 全局 `empty_stage.tscn` 保持中性。人物动作工作台是移动模块自己的完整场景，可以复用环境资源，但没有把移动专属输入、HUD 或动作逻辑写回全局空白工作台。
- 每个场景脚本保持单一职责；不建立「万能移动实验基类」。
- 所有新增模型、预览和导出资产另存并进入 Git；既有资产未被覆盖或删除。

子场景返回约定：七个场景的 Esc 与返回按钮都回到 `movement_lab_hub.tscn`；hub 的 Esc 与返回按钮回到顶层 `lab_hub.tscn`。

### 推进顺序（实际执行）

1. 人物动作工作台与镜头实验室先形成可运行代表链路。
2. 审计场景职责、三 Capability 边界和真实输入后，推广到御剑飞行与地形接触训练场。
3. 状态切换压力场复用前述结论，覆盖边缘时机和清账。
4. 最后在移动庭院做小范围回归、在群山宗门做组合验收；未把子实验的调试 UI 带入群山宗门。

集成阶段才把七个条目一次性登记为可运行（`exploring`）；此前清单中未落地的条目保持 `planned` 且无入口，界面如实显示「尚未落地」。

## 备选方案

- 继续在群山宗门中增加全部调试区域：局部问题难以隔离，且会破坏已经满意的综合场景，不采用。
- 每个子实验作为顶层模块：会把一个移动问题拆成多个伪玩法模块，污染八大模块目录，不采用。
- 先建立通用实验框架、万能镜头系统和公共基类：当前消费者不足，容易把尚未验证的假设固化为共享 API，不采用。
- 直接修改全局空白工作台承载人物动作：会让其他模块的中性起点依赖角色移动，不采用。
- 为跑动和动作切换新增 Capability：纯表现不具备独立玩法生命周期；当前先由表现层消费运动数据，不采用。若以后引入玩家主动冲刺、资源消耗或独立互斥，再单独评审新能力。

## 后果

- 顶层「角色移动」不再直接进入群山，而是先进入子实验目录；庭院与群山仍可直接启动，并各自返回子实验目录。
- 局部问题可以在隔离场景中复现与验收；镜头、动作、地形接触、飞行路线、状态清账各有独立验收报告与运行证据。
- `movement_lab_input.gd` 成为移动实验专属的输入状态对象，被两个以上场景消费；它不进 `core/`、不引用角色与能力，是「先出现第二个消费者再抽取」的实例。
- 清单状态成为进度的唯一真源：hub 的计数、可进入条目与禁用态都从数据推导，界面不再需要为每条入口单独改代码。
- 已知未完成：三项新场景的审美与手感待使用者试玩判断；镜头与动作两项在集成后仍需人工比较其主观质量。
- 已知限制：子实验目录改变了顶层角色移动入口，直接启动旧场景仍可用，但它们的第一跳返回是子实验目录而不是顶层目录。
