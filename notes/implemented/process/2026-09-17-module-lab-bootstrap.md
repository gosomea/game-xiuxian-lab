# Note: 独立 2.5D 模块实验工程初始化

Status: implemented

## 问题

使用者希望先独立探索地图、角色移动、剑法、小镇交流、人物成长与人物交互等模块，在模块具备可运行实验场景后再考虑完整游戏的玩法组织。2026-09-17 明确授权「开始新的空项目搭建」。新工程只以 game-template 为基线，完全摒弃 game-xiuxian-godot 的设计、代码、素材与运行依赖。

模板现有的「先验证完整核心循环才进入工程」流程与这一目标不匹配；模板生命系统示例也不能被计为新工程已完成的模块。

## 决策

- 新建 `projects/games/game-xiuxian-lab/`，以 game-template 0.4.0 实例化，作为当前大仓中的独立 Godot 工程。保留模板的核心设施、技能、Agent 入口、机械检查与架构历史。
- 项目定位为模块实验室。实验场景允许进入 `src/levels/`，无需先确定最终核心循环、胜负条件或十分钟完整流程。共享实现进入两级 `src/game/<domain>/<package>/` 叶子包；复杂度按实际复用需求增长。
- 实例化前先记录本决策，再落运行时代码。用户本轮授权覆盖初始化，无需重复审批。
- 模板的 vitals 示例移入 `src/tests/fixtures/template_vitals/`，仅用于保留基础回归覆盖；移除模板主场景与演示美术。核心七个脚本不改。所有移动在新副本首次导入之前完成，并由 Godot 重新生成缓存与路径检查验证。
- 主入口为实验目录。首批八项来自已讨论的模块清单，全部初始为 `planned`、无场景；选中后显示探索内容与依赖，不把计划伪装成可运行 Demo。
- 模块目录存于 `src/data/content/experiments.json`。状态为 `planned`（未建场景）、`exploring`（探索中，可选已有场景）、`ready`（已有可用场景，代表可供组合实验，不代表最终玩法完成）。`ready` 必须有有效 PackedScene；重复 ID、未知依赖、依赖环及虚假场景由目录契约测试拒绝。
- 提供独立空白 3D 工作台：X/Z 为地面，Y 为高度；正交俯视相机、参考网格、基础环境与灯光。它只验证工程能显示 3D 空间，不计入地图或角色模块，不固定最终美术与相机方案。
- 入口与工作台可直接启动，支持返回、重置视角与缩放；统一轻量 Theme。未做地图、角色、剑法、NPC、成长或背包玩法。
- 新测试只覆盖目录的真实状态与依赖契约；界面导航、工作台与窗口布局通过实际启动检查，不为外观编写镜像单元测试。

## 备选方案

- 在既有修仙项目继续拆模块：用户明确要求完全摒弃旧项目，因此不采用，也不迁移其中任何代码或素材。
- 先做一条十分钟完整体验，再拆模块：与用户先探索各模块、后考虑整体玩法的顺序相反，因此不作为本工程准入条件。
- 只复制模板原样交付：默认会进入生命系统示例，目录和项目约定无法表达本轮目标；改为真实的空白实验入口，原示例只保留为测试夹具。
- 一次把八个模块都做出占位场景：会让「空场景存在」混同于「模块已探索」，因此仅登记计划；本次只有单独标注的工程工作台可进入。

## 后果

工程可运行并具有清楚的后续实验入口，整体玩法保持未定。后续每个模块可独立确定目标、实现、调试与记录结论；组合实验按需要出现。模块的 `ready` 是当前探索范围内可复用的判断，不意味着最终数值、内容量或商业成品完成。

验证使用模板 Tier 0 检查与运行时测试，再实际观察主入口、工作台、返回路径和多窗口尺寸。运行截图与结果在 `docs/playtest/` 记录。应用外壳失败应修复外壳，不通过提前实现玩法来掩盖。
