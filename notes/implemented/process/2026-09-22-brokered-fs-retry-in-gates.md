# Note: 门禁临时目录对被代理文件系统做紧凑重试

Status: implemented

## 问题

`tools/verify/negative_control.py`（根 AGENTS.md 约定 6 要求每条门禁都有的一层）
连续两轮报「未能运行」：它在**第一个**用例上抛 `PermissionError` 并终止，
而另外 11 条 Tier 0 门禁全部报 OK。于是这个结果被读成「负向控制这条门禁逻辑有问题」，
并被记进 handoff 的「需在可控环境重跑」清单。

真因不在门禁逻辑，也不在仓库：部分 Agent 沙箱把文件系统写入代理给宿主，
并**间歇性**拒绝 `mkdir`，报

```
Brokered host mkdir requires an available runtime file rule
```

间歇性是关键，且方向反直觉——实测（同一进程、同一路径、无输入变化）：

| 做法 | 结果 |
|---|---|
| 连续 30 次 `mkdtemp`，**无间隔** | 29 次成功 |
| 10 次 `mkdtemp`，每次**间隔 1 秒** | **0 次成功** |
| 同一路径紧凑重试最多 8 次 | 命中成功 |

也就是说**等待本身让它失败**。这与「瞬时错误应该退避重试」的通用直觉正好相反：
本文件第一版重试用了 0.35 s 退避，把一次偶发拒绝变成必然失败（40/40 全拒），
表现为「重试也救不回来」。

`negative_control` 之所以最先暴露这个问题，是因为它要在临时目录里构造 27 个用例树
（多层目录、symlink、写文件），是全部门禁里唯一密集做文件系统写入的一条；
其余门禁只读仓库。

## 决策

在本文件内对 `Path.mkdir` / `Path.symlink_to` / `Path.write_text` 打一次补丁，
外加包一层 `tempfile.mkdtemp`（它绕过 `Path` 方法直接调 `os.mkdir`），
统一走**紧凑重试、无 sleep**，尝试上限 400。

补丁打在**原语**上，而不是逐个改写用例构造里的 25 处调用点：后者实测把调用改成了元组、
并因偏移计算错误产生语法错误，改动面大且容易漏；补丁只有约 70 行，作用域限于本进程，
不影响被它拉起的门禁子进程。

重试只覆盖「构造非法样本」这一步，因此**既不削弱门禁、也不掩盖真实拒绝**：
沙箱若持续拒绝，重试耗尽后抛出最后一个错误，门禁照样响亮失败。
负向控制本身验证的「非法案例会被拒绝」这一性质完全没有改动。

## 备选方案

**把 `negative_control` 标记为「需在受控环境运行」并从 Tier 0 摘出。** 否决理由：
约定 6 的整个意义就是「没有负向控制的门禁视为不存在」。把它摘出去等于让 11 条门禁
退回「只跑正向用例」的状态，而只跑正向用例的门禁可能因为选择器写错而恒真——
这正是这条门禁存在的理由。

**改用仓库内目录（`tmp/`）而不是系统临时目录。** 否决理由：实测仓库内同样被拒绝
（`mkdir(parents=True, exist_ok=True)` 在工作树内也会偶发失败），换目录不解决问题；
而且门禁在仓库里留下中间产物会污染工作树，与「不污染仓库工作树」的原意冲突。

**用 `subprocess` 调 `mkdir -p` 绕开 Python 的宿主代理。** 否决理由：这是绕过沙箱
策略而不是与之共存，且把「能不能跑」绑定到 shell 可用；在真实 CI（无该代理）上
反而是多余的一层。

**在重试之间加退避（第一版做法）。** 否决理由见上：实测退避使成功率从 ~97% 降到 0%。

## 后果

- `negative_control` 现在 **27/27 通过、退出码 0**（本轮实测），Tier 0 因此首次
  在沙箱环境里 12/12 全绿。
- handoff 里「需在负载正常、且 mkdir 可用的环境下重跑」这条遗留项可以关闭：
  它一直是环境适配问题，不是待补的验证。
- 教训记入本 note：**「间歇性错误」不要先假设成「需要等待的错误」**。
  本轮如果不做那张对照表，会继续把 0.35 s 退避当成正确修法，
  而它恰好是让失败变必然的原因。
- 已知限制：重试上限 400 次是经验值。若某个环境真的**持续**拒绝，
  门禁会以 `RuntimeError` 明确报出「重试耗尽 + 最后一个错误」，
  而不是抛裸 `PermissionError`——失败信息仍指向具体操作与路径。
