# Note: 历史大文件迁入 Git LFS

Status: implemented

## 问题

前向 LFS 与轻量动作源已控制新版本增长，但原 Git pack 仍约 3.88 GiB。其中约 3.80 GiB 是当前分支可达历史，大于 5 MB 的文件对象占约 3.25 GiB。删除工作树文件或反复普通 GC 无法消除这些历史对象。

## 决策

使用者于 2026-10-10 明确授权迁移历史大文件。本决策接替[资产增长方案](2026-10-09-repository-binary-growth.md)中“历史不迁移”的范围限制；独立动作源和共享几何的决策继续有效。

1. 先独立备份原 Git 元数据、所有引用、reflog、不可达对象及已有 LFS 对象，再在独立副本操作。原主分支基点为 `dbbcfb5961254b289cf3b235fadb3bd632956dd5`。备份保留在仓库外，不作为迁移后的日常 Git 引用。
2. 用 `git lfs migrate import --include-ref=refs/heads/main --above=5000000b --object-map=...` 改写主分支全部历史。阈值严格为大于 5,000,000 bytes，不限后缀，包含历史 FBX、ZIP、VRM 和已有备份；没有删除任何资产，也不将历史完整模型改为轻量派生文件。
3. 保存旧提交到新提交的映射。逐提交核对路径、文件模式和所有普通文件内容；迁移出的 LFS 对象用 SHA-256 与原始 blob 内容校验，已有 LFS 指针继续对应原对象。仅 `.gitattributes` 允许因迁移增加追踪规则。
4. 保留未迁移的小旧资产的普通 blob 豁免，从基线移除已迁入 LFS 的文件；后续任何大于 5 MB 的新文件必须走 LFS。新 `.blend/.glb/.obj` 仍全部走 LFS，新 `.blend1` 自动备份仍拒绝提交，已有跟踪备份保留。
5. 迁移仓库验收完成后替换本地 Git 元数据，工作树资产保持真实文件。旧元数据在独立备份保存；日常引用不再指向旧历史，否则旧 pack 仍无法回收。远端主分支保留真实旧提交用于 `--force-with-lease` 校验，但不在本地创建指向旧历史的跟踪引用。
6. 普通 Git pack 与 LFS 资产缓存分别计量。LFS 是按版本保存完整文件的资产存储，不承诺总磁盘或账号存储缩小。历史大于 5 MB 的唯一内容预估 9.08 GiB，上传前须核验账号余量和预算。当前账单 API 缺少 `user` scope，不能确认余量；本轮不扩展凭据权限、不设置预算、不强推，完成本地迁移与可审查验收。

实施证据、备份位置、实际大小与复现命令记录在 `docs/migrations/2026-10-10-historical-lfs/`。检查遵循 flow-pre-push-checks；项目导入与运行时测试必须在真实资产恢复后完成。

## 备选方案

- 仅清理不可达对象：当前约 83 MiB，收益不足且会失去恢复对象，保留在备份。
- 仅运行 aggressive GC：不改变存储边界，收益不确定，不能解决历史全量人物版本增长。
- 删除历史资产或重新初始化只留最新快照：损失探索成果或提交记录，不采用。
- 将全部小图片也迁入 LFS：增加下载和完整版本计费；本轮历史迁移采用 5 MB 阈值。
- 把旧历史备份为迁移仓库内的分支或检查点：会继续保留旧 pack；备份放在独立 Git 数据库。

## 后果

主分支提交号改变，后续远端发布需要明确授权、核验 LFS 配额并采用预期旧提交的 `--force-with-lease`。其他已有克隆须重新克隆或按提交映射迁移本地工作，不能把旧分支合回新历史。

这次迁移将 Git 历史中的大文件内容替换为 LFS 指针，所有资产版本仍可通过对应历史提交及 LFS 对象恢复。备份是恢复迁移前历史的独立副本，不能代替项目资产继续进入本仓 Git/LFS 的要求。
