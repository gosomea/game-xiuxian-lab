# Note: src 按功能分包而非按技术类型分包

Status: implemented

Superseded: 2026-09-02 — 目录仍按功能内聚，但单层 `features/<name>/`、`game/<功能>/` 与“feature 可大到子系统”的粒度规则已由 `2026-09-02-two-level-gameplay-packages.md` 取代；以下正文保留为 0.2 历史。

## 问题

初版 `src/` 按技术类型分层：`capabilities/`、`components/`、`sheets/`、`core/`。结果是**单个功能被拆散到多个目录**——模板原有的示例功能 6 个文件分布在 4 个目录。

具体代价：

- **改一处要跳四处**：给功能加一个参数，需在 `components/` 改数据、在多个 `capabilities/` 改读取、可能还要改 `sheets/` 装配。
- **删除不可靠**：砍掉一个功能需记得删四个位置；漏删的孤儿文件不会被任何门禁发现（它们语法合法、结构合规）。
- **资源无处安放**：Godot 的场景、材质、贴图、音频属于功能而非「技术类型」，只能堆进全局 `assets/`，与功能的关联仅靠命名约定维持。
- **Agent 上下文成本**：理解一个功能需要打开 4 个目录；按功能分包只需读 1 个。对 AI Native 仓库是直接损失。
- **认知边界与代码边界不一致**：人和 Agent 谈论的单位是功能，目录的单位却是技术类型。

按技术类型分层本应带来「同类集中便于横向比较」，但该收益在本架构下不成立：Capability 之间禁止互相引用（铁律 2），无横向比较需求；集中视图已由 `design/capability_catalog.json` 提供。

## 决策

`src/` 按功能分包：

```
src/
├── core/              # 框架层，保持按层组织
├── features/<name>/   # 一个功能一个自包含包：数据 + 能力 + 配对测试 + Sheet + assets/
├── shared/            # 跨功能共享 Component，准入需 notes 决策（按需创建）
└── demo/              # 示例场景，可整体删除
```

**判据：一个功能包必须可整体删除而不留孤儿。**

配套决定：

**`core/` 不按功能分。** 框架层的基类与全局设施本身就是跨功能基础设施，强行编功能包只会制造无意义嵌套。

**`shared/` 设准入门槛。** 它是按功能分包最常见的失败点——会逐渐变成「不知道放哪就放这里」的垃圾场，最终退化回按类型分层。准入需显式 notes 决策；首发不预建。

**Sheet 按文件名后缀 `_sheet.tscn` 识别**，不再靠所在目录（`src/sheets/`），使 Sheet 可与其功能同处一包。

**门禁改为按内容发现**：`verify_capabilities` 与 `gen_capability_catalog` 扫描 `src/` 全部 `.gd` 取 `extends Capability` 者，不再遍历固定路径。原「目录名必须等于主脚本名」约束随之取消——它与「一个功能包含多个能力」直接冲突。新增要求：Capability 必须声明 `class_name`（按类名识别），配对测试必须与被测脚本**同目录**（要求加强而非放松）。catalog 条目新增 `feature` 字段，可按功能聚合。

**新增风险与其兜底**：同包内两个能力物理相邻，会增加直接引用的诱惑。该风险由 `verify_capabilities` 的跨能力引用检查机械兜住（基于类名匹配，不依赖路径距离），并在 `src/AGENTS.md` 显式警告「同一功能包内的能力之间同样禁止直接引用」。负向控制新增对应用例（同包互相引用必须被拒）。

## 备选方案

- **保持按技术类型分层**：输在功能内聚。其主要论据「同类集中便于横向比较」在本架构下不成立（能力互不引用，且 catalog 已提供集中视图）。
- **混合方案：能力按功能分包，Component 与 Sheet 仍集中**：输在没解决核心问题。功能仍会被拆到三处，删除仍不可靠，资源仍无处安放。这是最易达成的妥协，但保留了大部分代价。
- **完全扁平（所有文件平铺 `src/`）**：输在规模。十余个文件时可行，内容扩张到数百文件后无任何导航结构。
- **按玩家可见系统分包（`systems/battle/`）**：输在粒度僵化。系统边界比功能边界粗，一个「战斗系统」会长成几十个文件的巨包，内部仍需再分。功能粒度更细且可组合成系统；将来确需系统层级时，`features/` 下再嵌一层即可，不影响本决策。
- **命名用 `game/` 或 `gameplay/`**：语义相近。选 `features/` 因其粒度中立（一个 feature 可小到单个能力、大到子系统），且不与 `design/content/`（数据层）混淆。

## 后果

- 代价：门禁的发现方式依赖 `extends Capability` 文本匹配，若某能力通过中间基类间接继承会被漏检（深层继承链的支持留待真实需求）；文件移动后 Godot 需重新 `--import` 重建 `.uid` 与场景引用缓存。
- 收益：功能自包含，改动与删除均在单一目录内完成；资源有了归属位置；Agent 理解一个功能只需读一个目录。
- 验证：示例功能包 `features/vitals/` 6 个文件同处一目录；11 条门禁全绿；22 项负向控制全部仍被拒（含新增的同包引用与缺 class_name 用例）；47 条运行时断言通过。
