# Note: 控制人物资产带来的仓库体积增长

Status: proposed

## 问题

2026-10-09 本机 `.git/objects` 为 8.62 GiB 松散对象，`git count-objects -vH` 显示 `packs: 0`。工作树里每个动作版本各有一份约 60 MB 的 `.glb` 和一份约 57 MB 的 `.blend`，内容不同，Git 不能按相同贴图去重。继续按「整份网格 + 内嵌贴图 + 动作」另存新版本，远端会先碰到 GitHub 对单文件 50 MB 警告和 100 MB 拒绝。

本机没有 `git-lfs`，仓库没有 `.gitattributes`。`refs/codex/turn-diffs/checkpoints/...` 仍指向含试验 GLB 的检查点；只要该引用还在，对应 blob 就不会被回收。删除该引用会丢掉检查点，本提案不包含这一步。

当前树里 5 个 `.blend1` 都在 `docs/art/` 下，单个 151–251 KB，不是体积来源。它们是 Blender 自动备份，是否算探索资产还没有决定，因此本提案不删除它们。

## 提案

本地打包已经做过，不改历史、不删资产、不推送。2026-10-09 `git fsck` 无输出且退出码为 0，随后 `git gc`：松散对象从 8.62 GiB、0 个 pack，变为 2 个 pack、3.88 GiB，`.git` 从 8.6 GB 降到 3.9 GB。Codex 检查点引用仍在。

之后的新版本才改变存放方式，且都要另一次确认后才能落地：

1. 为以后新提交的 `*.blend`、`*.glb`、`*.blend1`、大于 5 MB 的 PNG 和 OBJ 启用 Git LFS。只跟踪新提交，不迁移、不改写已有历史。落地前安装 `git-lfs`，并确认 GitHub LFS 配额够用。
2. 新动作版本只导出骨骼动画，网格和三张贴图继续引用现役共享文件，避免每版再内嵌约 30 MB 贴图。这会改美术导出脚本和 Godot 场景引用，要单独改生成器并复测现役人物。
3. 把 `.blend1` 定为临时备份而不是源资产：以后不提交新的 `.blend1`；已经在库里的 5 个小文件保持不动，除非使用者明确要求删。

## 备选方案

- 现在把历史里的大文件迁到 LFS：必须改写历史并强推，当前授权不允许。
- 删除旧 `.blend` / `.glb` 来腾出空间：违反探索资产保留，不采用。
- 只把大文件写进 `.gitignore`：资产会留在本机却不进仓库，违反「所有项目资产必须进入 Git」。
- 把现有 5 个 `.blend1` 立刻删掉：体积可忽略，而且它们算不算源资产还没确认。

## 验收标准

- 本地打包已满足：`packs` 为 2，`.git` 为 3.9 GB，低于打包前的 8.62 GiB；打包前 `git fsck` 退出码为 0。
- 未执行 LFS、未改导出管线、未删除 `.blend1`、未删除 Codex 检查点引用、未推送。
- 若使用者确认第 1 条，新提交的大文件走 LFS，已有历史中的 blob 路径不变。
- 若使用者确认第 2 条，新版本 GLB 不再内嵌三张贴图，现役场景仍能加载同一套网格与贴图。

## 风险

LFS 配额或未安装客户端会让新克隆拿不到大文件。拆分动画导出如果引用错版本，人物会穿到旧网格。打包只减少本机松散对象，不会减小已经推送过的远端历史。
