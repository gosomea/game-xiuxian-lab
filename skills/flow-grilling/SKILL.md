# flow-grilling

用追问把使用者脑中的决策树完整走一遍，直到没有被默默假设的东西。**本文件是指引，不是清单脚本。**

方法吸收自 [mattpocock/skills `grilling`](https://github.com/mattpocock/skills)（MIT，2026-08-28 吸收）。此处为 Agent 无关重写：不依赖 slash command、不依赖任何特定 Agent 的 Skill 调用机制，任何 Agent 读本文件即可执行。

## 为什么需要它

问题不是「使用者需要写更长的需求」，而是**使用者自己也不知道自己想要什么的全部细节**。脑中有一整棵决策树，说出口的只有树根那一个节点，剩下分支全靠 Agent 猜——猜对是运气，猜错就返工。

本方法把模糊性从代码里（返工成本高）前移到对话里（成本近零）。

## 核心机制：frontier 分轮提问

把决策画成树。**frontier** = 所有「前置依赖已经确定」的决策，即现在就能问、不需要猜测未知答案的问题。

1. 算出当前 frontier，**一次问完整个 frontier**（不是一次一问，也不是一次问全部）。
2. 每个问题编号，并**给出你的推荐答案**。
3. 等使用者回答完这一轮，再算下一轮。
4. 答案依赖本轮未决问题的，属于**后面的轮次**，不要提前问。

每轮回答都会重塑树：已定的决策把 frontier 向外推，解锁依赖它们的问题。

**终止条件**：frontier 为空——每个分支都访问过。

## 提问格式

```
❓ **Q1** — **<问题标题>**：<问题正文，可含多个选项>

➡️ <你的推荐答案>

---

❓ **Q2** — **<问题标题>**：<问题正文>

➡️ <你的推荐答案>
```

## 事实与决策分离（提高追问密度的关键）

**事实是你的职责，永远不是使用者的。** 环境里能查到的就自己查：文件系统、`design/capability_catalog.json`、`src/data/vocabulary/index.json`、现有 `notes/`、上游文档。

不要因为查事实而阻塞：正在进行的查询是一个「未决前置」，**只有依赖它的问题需要等**，frontier 上其余问题照问。

**决策是使用者的。** 「选 A 还是 B」「要不要做这个」逐个提交并等待回答，不代为决定。

## 硬性约束

**未达成共识前零动作。** 追问阶段纯对话——不写文件、不改代码、不建目录。使用者明确确认「我们已达成共识」后才进入实现。这与根 `AGENTS.md` 铁律 3（先决策记录，后实现）同源。

**规模上限**：4 轮约 46 个问题属正常。接近 200 个问题说明议题范围过大，且上下文填满后提问质量会下降。此时停止，改用 `flow-wayfinder` 先画地图再分块。

## 两个失败模式（必须显式警告使用者）

**被动（主要失败模式）**：使用者连续同意 40 次推荐答案，最终得到一份 Agent 写的、他只是点头的方案——看似高产，实则什么都没决定，却带着未挣得的确定性。

检测与应对：若使用者连续 5 次以上无异议地采纳推荐答案，主动指出并要求他至少反驳一次或说明为什么全部同意。**反驳本身就是更高效的思考。**

**停留过久**：一直追问，永远不动手。frontier 空了就结束，不要为了显得周全而制造问题。

## Grillable 与 Ungrillable

有些问题追问不出答案，**必须有东西可反应才能回答**：

| 类型 | 例子 | 处理 |
|---|---|---|
| Grillable | 「转世后继承什么」「寿元用完算失败还是转世」「战斗要不要玩家操作」 | 继续追问 |
| **Ungrillable** | 「这个手感对不对」「这个节奏够紧张吗」「这个交互该是什么感觉」 | **停止追问**，走 `flow-prototype` 做可丢弃原型，看过之后一句话就能回答 |

**硬聊 ungrillable 问题是 session 膨胀的首要原因。** 识别到就切换，不要试图用文字描述解决体感问题。

## 起效的判据

- 使用者会产生反对意见（全程点头说明问得不够尖锐）
- 问题分多轮到达，且后轮明显建立在前轮答案之上
- 会走到意料之外的地方（如果结论和开场设想完全一致，说明只是在复述）
- 结束时每个选择都能向一个不在场的人辩护

## 排除

- 不在追问阶段修改任何文件。
- 不把使用者没说过的偏好当作已确认（不确定就问）。
- 不为了凑轮数制造无实质决策价值的问题。
- 不追问 ungrillable 问题（转 `flow-prototype`）。
