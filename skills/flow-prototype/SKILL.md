# flow-prototype

做一个**预期会被丢弃**的原型，回答一个用讨论回答不了的问题。**本文件是指引，不是清单脚本。**

方法吸收自 [mattpocock/skills `prototype`](https://github.com/mattpocock/skills)（MIT，2026-08-28 吸收），并加入本仓探索期纪律。

## 铁律：原型不进本仓的建造纪律

原型**不写 notes、不过门禁、不配测试、不登记词汇表、不进 `src/`**。

理由不是省事，而是：给一次性原型上工业标准会产生沉没成本感，**让人舍不得扔掉不好玩的设计**——而尽快扔掉不好玩的东西正是原型存在的唯一目的。

存放位置：仓库外的临时目录，或 `prototypes/`（已在 `.gitignore`）。**不要放进 `src/`**，哪怕「以后可能改改就能用」——这个想法本身就是沉没成本在说话。

## 起手式：写下要回答的那一个问题

动手前先明确：**这个原型回答哪一个问题？答案会是什么形式？**

| 好的原型问题 | 坏的原型问题 |
|---|---|
| 「权衡寿元与收益这个决策，玩起来有压力感吗」 | 「做一个修仙游戏原型」 |
| 「35° 俯角下六边形地块关系看得清吗」 | 「验证一下 2.5D 效果」 |
| 「三种构筑路线打起来有明显区别吗」 | 「测试战斗系统」 |

写不出具体问题，说明还该回去做 `flow-grilling`。

## 工作流

1. **定问题**：一句话，且答案可判定（是/否，或三选一）。
2. **选最便宜的载体**：能用纸笔就不用 Excel，能用 Excel 就不写代码，能用单文件 HTML 就不开引擎。**载体越易丢弃越好。**
   - 数值/策略类 → Excel 或单文件 HTML
   - 手感/动作类 → Godot 灰盒（白方块 + 白地面）
   - 视觉/构图类 → 引擎灰盒 + 占位色块，或直接画图
3. **只做回答问题所需的最少内容**：不做存档、不做 UI 框架、不做菜单、不做美术、不做架构、不做设置项。
4. **实际玩/看**，不是「看代码觉得没问题」。手感与节奏类问题必须实机运行观察，截图不作为证据。
5. **写下答案**（一两句话），把答案带回 `flow-grilling` 或 `flow-zero-to-one` 继续。
6. **丢弃原型**。若确实要保留某段实现，明确说明保留哪一段、为什么，并按 `flow-add-capability` 重新实现进 `src/`——**不是把原型代码搬进去**。

## 判断原型是否成功

成功 = **拿到了那个问题的答案**，不是「原型能跑」。

一个跑得很顺但没回答问题的原型是失败的；一个丑陋、崩溃、只跑了 10 秒但让你确定「这个不好玩」的原型是成功的——它省下了几周。

## 排除

- 不追求代码质量、不写测试、不做错误处理。
- 不在原型里做「顺便也试试」的第二个问题（一次一个问题；有第二个问题就做第二个原型）。
- 不把原型代码直接搬进 `src/`。
- 不因为「已经写了这么多」而保留一个证明玩法不好玩的原型。
