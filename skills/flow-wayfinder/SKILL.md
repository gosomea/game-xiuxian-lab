# flow-wayfinder

议题太大时，先把工作画成地图，再在地图的每一块里分别做追问。**本文件是指引，不是清单脚本。**

方法吸收自 [mattpocock/skills `wayfinder`](https://github.com/mattpocock/skills)（MIT，2026-08-28 吸收）。它不是纯任务拆解——它是 `flow-grilling` 的规模化形态：地图只负责划分边界，每块内部仍然靠追问推进。

## 何时该用它（明确判据）

| 现象 | 判断 |
|---|---|
| `flow-grilling` 问题数接近 200 | 议题过大，转本 skill |
| 追问明显开始重复、后轮质量下降 | 上下文已填满（dumb zone），转本 skill |
| 使用者的诉求横跨多个里程碑 | 直接从本 skill 开始 |
| 单个功能、单个决策 | **不要用本 skill**，直接 `flow-grilling` |

## 工作流

1. **确认议题边界**：这次要覆盖什么、明确不覆盖什么。写不出「不覆盖什么」说明边界还没想清。

2. **画地图**：把议题切成块。切法优先级：
   - 按**可玩性风险**切（最高风险的先做）——推荐，见下节
   - 按**玩家可见的体验单元**切（探索 / 战斗 / 成长 / 元循环）
   - 按技术依赖切——**最后考虑**，因为它会把低风险的基建排在前面

3. **给每块标注**：它回答什么问题、依赖哪些块、风险等级（如果这块结论是坏的，整个议题该不该重做）、是 grillable 还是 ungrillable。

4. **排序**：**按风险从高到低**，不是按技术依赖从底到顶。理由见下节。

5. **逐块推进**：每块单独开一次 `flow-grilling`（grillable）或 `flow-prototype`（ungrillable）。**一块结束后把结论带回地图**，因为它可能改变后续块的排序或让某块变得不必要。

6. **地图随结论演进**：地图不是一次画完就冻结的计划。每块的结论都可能新增块、删除块、改变排序。

## 为什么按风险排序而不按依赖排序

技术依赖顺序（自底向上）会让你先做存档系统、资源管理、UI 框架、输入系统——**全是低风险的确定性工作**，做起来舒服有进度感，但等做到核心玩法时热情已经耗尽。而核心玩法才是唯一可能证明整个项目该死的东西。

按风险排序意味着：**先做「如果这个结论是坏的，整个项目该重做」的那一块。** 坏消息越早到越好。

依赖关系仍然要遵守（做不了就是做不了），但在**同等可做**的块之间，风险高的先做。

## 产出

一份地图（可以就写在对话里，不必落盘）：每块的名称、要回答的问题、风险等级、grillable/ungrillable、依赖、当前状态（未开始 / 进行中 / 已结论）。

若议题会跨多次会话，把地图写进 `notes/proposed/` 作为一篇决策记录——此时它已经不只是地图，而是一个待评审的推进方案。

## 排除

- 不在画地图阶段做任何实现。
- 不把地图当成冻结的排期计划（它必须随结论演进）。
- 不为了地图完整而拆出没有实质问题要回答的块。
- 不用本 skill 处理单个决策（那是 `flow-grilling` 的工作，用本 skill 是过度设计）。
