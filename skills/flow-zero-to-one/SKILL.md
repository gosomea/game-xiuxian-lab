# flow-zero-to-one

把「想做个游戏」变成「知道明天该写哪个 Capability」。**本文件是指引，不是清单脚本。**

产出契约吸收自 [DY-2026/GameDesignOS](https://github.com/DY-2026) 的 concept-architect（MIT，2026-08-28 吸收）；追问与原型方法见 `flow-grilling` 与 `flow-prototype`。

## 铁律：①–⑤ 在模板外进行

```
模糊偏好 →① 偏好显性化 →② 概念候选 →③ 概念结构化 →④ 压力测试 →⑤ 脏原型验证 →⑥ 建造
         └──────────── 模板外：不写 notes、不过门禁、不进 src/ ────────────┘  └─ flow-add-capability ─┘
```

探索期与建造期需要相反的纪律。门禁、notes、强制测试是为「已知要做什么」设计的；用在探索期会让人**舍不得扔掉不好玩的设计**。第⑥步才开始受本仓纪律约束。

## ① 偏好显性化（必须先于②）

**「我完全没有 idea」是不准确的自我描述。** 真实状态是有大量模糊偏好但未被提取：玩过几百小时的某类游戏、某个机制让人着迷、某种设计让人受不了。

**为什么这步必须在前面**：跳过它直接做②，产出的是使用者自己不相信的方案。独立游戏做不完的首要原因不是技术，是做到一半发现自己不喜欢这个东西。而 Agent 特别擅长生成看起来合理但使用者毫无热情的方案。

用 `flow-grilling` 的分轮方式问，方向包括：

- 最近让你停不下来的游戏是什么？**具体是哪个瞬间**让你停不下来（不要答「玩法好」，要答「那一下我做了什么」）
- 有没有哪个游戏你玩了很久但其实不快乐？为什么还在玩？
- 什么设计让你直接退款/卸载？
- 你希望玩家玩完你的游戏后，跟朋友怎么描述它？
- 你自己愿意反复做一百次的动作是什么？
- 你**不想**做什么类型？（这条常常最有信息量）

**产出**：一份偏好清单，含至少 3 条「必须有」和 3 条「明确不要」。

## ② 概念候选生成

三种方法并用，每种出 2–3 个候选：

**verb-first（推荐主路径）**：先定核心动词，再包题材。动词是玩家反复做的那个动作。
- 例：「权衡不可再生资源换取成长机会」→ 可以是修仙（花寿元换突破率），也可以是航海、探险、政治。**动词先于题材。**
- 判据：一句话说完动词后，一个没听过你项目的人能立刻明白「玩这个在干什么」。

**mashup（异质组合）**：两个不相干品类的核心机制强行组合，看有没有化学反应。
- 不要组合同类（Roguelike + 卡牌 = 已被做烂）
- 要组合异质（Roguelike + 报纸编辑 / 塔防 + 语言学习 / 生存 + 官僚流程）

**MDA 逆推（从目标体验反推机制）**：先定「玩家该有什么感受」，再倒推什么机制产生它。
- 「我要玩家感到孤独」→ 无 NPC 对话、长距离移动、稀有的他人痕迹
- 理论参考：`design-game-theory`（MDA 框架、心流通道、Bartle 玩家类型）

**产出**：3–6 个概念候选，每个一句话动词 + 一句话题材。

## ③ 概念结构化

对①的偏好清单筛出的 1–2 个候选，各写一份结构化契约：

**核心动词**：玩家反复做什么，为什么有趣（有趣性来源必须写明：稀缺决策压力？技巧精进？意外发现？社交表达？）

**player-promise（对玩家的承诺）**：一句话，玩家买这个游戏得到什么体验。它应该能直接当 Steam 商店页第一句话。写不出来说明概念还模糊。

**core loop（核心循环）**：3–6 步的闭环，末步必须回到首步。标注每步的时长量级。
```
例：探索(2分) → 遭遇(3分) → 构筑调整(1分) → 突破尝试(30秒) → [失败]转世继承 → 探索
```

**assumption ledger（假设账本）**：把所有支撑这个概念的判断按证据强度分级——探索期九成内容是假设，**不要把猜测伪装成事实**。
| 级别 | 含义 |
|---|---|
| `provided` | 使用者明确说过的 |
| `derived` | 从 provided 逻辑推出的 |
| `assumption` | 你在假设，未经验证 |
| `unknown` | 知道不知道，需要决策 |
| `needs_research` | 需要外部信息才能回答 |

**scope gate（范围闸门）**：每个特性归入一档。**最后两档最重要**——明确写下不做什么比排期更能防范围失控。
| 档位 | 含义 |
|---|---|
| MVP | 证明核心动词有趣所需的最小集合 |
| Vertical Slice | 一条完整体验链（可给人试玩） |
| Demo | 可公开的试玩版 |
| Release | 首发内容量 |
| Post-launch | 上线后 |
| **暂不做** | 认可但明确推迟 |
| **建议砍掉** | 判断为不该做，写明理由 |

**validation plan（验证计划）**：每个关键假设配一个验证方式与**通过/失败标准**。失败标准必须写，否则不叫验证。

## ④ 压力测试

用 `flow-grilling` 打③的产出。重点攻击：

- assumption ledger 里所有 `assumption` 级条目——凭什么这么认为？
- core loop 的每一步——玩家为什么要走这一步而不是跳过它？
- player-promise 与核心动词是否真的一致？
- scope gate 的 MVP 档是否还能再砍？（几乎总是能）
- **哪些问题是 ungrillable 的？**（手感、节奏、观感）标记出来交给⑤

## ⑤ 脏原型验证

对④标出的 ungrillable 问题，以及 MVP 档的核心动词，走 `flow-prototype`。

**这一步的唯一目的是拿到「这个动词有趣吗」的答案。** 一个丑陋、崩溃、只跑了 10 秒但让你确定「这个不好玩」的原型是成功的——它省下了几周。

原型结论会反过来改动③的契约，甚至否决整个概念。**否决是好结果**，回到②换候选。

## ⑥ 进入建造期

只有当以下全部成立时才进入：

- 核心动词已被原型验证有趣（不是「我觉得会有趣」）
- player-promise 能一句话说清
- core loop 闭环且每步有存在理由
- scope gate 的 MVP 档已砍到最小
- assumption ledger 中影响架构的假设已降级为 `derived` 或 `provided`

然后：
1. 把③的契约转写为 `design/pillars.md`（设计支柱）——**这是探索期唯一进入本仓的产物**。
2. 把 scope gate 转写为 `docs/roadmap.md`。
3. 关键设计决策写入 `notes/proposed/`（含备选方案），评审后转 implemented。
4. 之后走 `flow-add-capability` 逐个实现能力。

议题太大装不进一次会话时，用 `flow-wayfinder` 先画地图。

## 排除

- 不在①之前生成概念（会产出使用者自己不信的方案）。
- 不在⑤通过之前写任何 `src/` 代码。
- 不把原型代码搬进 `src/`。
- 不跳过 scope gate 的「建议砍掉」档（不写下不做什么，范围一定会失控）。
- 不把 `assumption` 当 `provided` 用。
